# EOSIntegrationKit local source audit

Audited 2026-10-02. `EIK_ROOT = F:\EOSIntegrationKit-main (1)\EOSIntegrationKit-main`.
Every `Source/...:line` reference below is relative to that root, not CkPlugins. Line numbers are one-based and refer to the supplied archive. This is a source inspection, not a build, packaged-game test, network test, service-policy audit, or confirmation of portal configuration. The archive was read only. The only authored file is this report.

## Identity, completeness, and license

- Descriptor: `EOSIntegrationKit.uplugin:3-4` declares integer version 3 and version name **4.85**; `:13` declares **UE 5.6**. Nine modules are listed. All general modules allow Win64, Android, Mac, Linux and exclude iOS; DiscordGame allows Win64 only; EIKEditor is editor-only; EIKVoiceChat is ClientOnlyNoCommandlet. Presence of iOS code does not mean iOS is enabled by this descriptor.
- This is the older OnlineSubsystem-based implementation. It does not contain the newer `EIKCore` / `IEIKOnlineServices` implementation discussed in current public EIK documentation. Treat current website documentation as a separate version until a matching source release is supplied.
- Inventory of `Source`: 242 `.cpp`, 260 `.h`, 13 `.cs`, plus Android AARs, iOS embedded frameworks, platform glue and resources. There is no supplied example project/content directory and no discovered test-named files. These counts include platform and external-support files and are not a code-size or quality metric.
- **The archive omits the EOS SDK payload.** `Source/ThirdParty/EIKSDK` has build rules, platform XML and two Android-specific headers, but no general `eos_version.h`, normal EOS headers, SDK Bin/Lib files or SDK tools. `.gitignore:73-82` explicitly excludes these. `Source/ThirdParty/EIKSDK/EIKSDK.Build.cs:129-168` expects SDK headers/import library/runtime DLL and stages them. The source cannot establish the actual EOS SDK version, ABI compatibility or a build-ready package. Discord libraries are also external/missing from the file inventory; build rules conditionally handle their availability.
- **License inconsistency:** `README.md:59-61` advertises MIT, while `LICENSE:1` says use is governed by the Unreal Engine EULA. Many implementation files carry Epic copyright/all-rights-reserved notices. Do not infer MIT permission to copy/relicense this implementation from the README. Resolve the applicable permissions before reuse. This is an observed file inconsistency, not a legal conclusion.

### Automatic setup has source-file side effects

`Source/EOSIntegrationKit/Private/EOSIntegrationKit.cpp:13-15` invokes ConfigureOnlineSubsystemEIK at module startup. When `/Script/EOSIntegrationKit.EIKSettings` has bAutomaticallySetupEIK enabled (`:31-44`), it loads the project's `Config/DefaultEngine.ini` as text, adds the OnlineSubsystemEIK enabled section, replaces/adds DefaultPlatformService=EIK in OnlineSubsystem (`:48-95`), appends driver configuration and version-specific NetDriverDefinitions (`:100-133`), and saves the file (`:139-148`). On UE 5.6 the new Engine.Engine block includes ClearArray plus game and beacon drivers with IpNetDriver fallback. If the target driver section already exists, the helper does not comprehensively merge all driver entries; it primarily detects section text.

The settings property-change handler similarly edits DefaultEngine.ini when the automatic setup property is changed (`Source/EOSIntegrationKit/Private/EIKSettings.cpp:493-542`) and may restart the editor after its dialog (`:562-565`). The SaveConfig/Flush block at `:400-413` is commented out; it is not an active credential persistence feature. `ConfigureDedicatedServerConfigEIK` currently only computes a WindowsServer Engine.ini path (`EOSIntegrationKit.cpp:169-172`) and does not write a dedicated-server setup.

Editor startup also warns if EOSCore or OnlineSubsystemRedpoint is enabled (`EOSIntegrationKit.cpp:16-26`), citing duplicate SDK integration. This is evidence of coexistence assumptions in this archive, not proof every possible two-provider integration is invalid. A Ck replacement should use explicit reviewed configuration/migration for provider and drivers rather than silently rewriting unrelated project networking settings at module startup.

## Login flow traces and identity contracts

### 1. High-level Auth -> Connect -> ready

1. `EIK_LoginwithAuth_AsyncFunction.cpp:8-32` creates a Blueprint async UObject, builds encoded credential type `eas_+_<credential>_+_<external>`, subscribes to the UE identity completion delegate and calls login for local user 0.
2. `UserManagerEOS.cpp:707-732` stores last credentials and selects encoded Auth path. `:909-1001` decodes enums and copies configured login scopes into EOS Auth options.
3. `:1007-1059` calls EOS_Auth_Login. Success enters ConnectLoginEAS. InvalidUser enters LinkEAS using the continuance token; this is an Auth linking operation, distinct from EOS Connect PUID creation.
4. `:1310-1353` copies the EOS Auth access token, sets external credential type EPIC and calls EOS_Connect_Login. Success calls FullLoginCallback with EpicAccountId and PUID; InvalidUser calls CreateConnectedLogin/Connect_CreateUser (`:1485-1509`). Other failures log and log out.
5. `:1523-1610` installs auth-status, friends, presence and Connect-expiration notifications, adds local identity/account mappings, then emits UE login/status delegates. Gameplay “ready” should distinguish Auth identity, Connect identity and initial social query readiness; this code's login success does not prove every friend/presence query has completed.

### 2. Connect-only external/platform/guest identity

1. `AsyncFunctions/Login/EIK_Login_AsyncFunction.cpp:15-39` creates `noeas_+_<external credential>`, supplies display name/token and calls UE identity login for user 0.
2. `UserManagerEOS.cpp:624-669` maps the external enum and builds EOS Connect credentials/user-login info.
3. `:1062-1098` completion: Success -> CompleteDeviceIDLogin; NotFound with device-ID type -> CreateDeviceID -> retry Connect; InvalidUser -> CreateConnectID with continuation token -> CreateUser -> CompleteDeviceIDLogin. It automatically creates a fresh product user rather than exposing an explicit existing-account choice.
4. `:527-578` installs Connect-status and expiration notifications, adds a local user with null EpicAccountId, emits completion. Friends notification and EAS presence setup in FullLoginCallback are not part of this branch.

The account identifiers must remain distinct: EpicAccountId for EAS friends/presence/ecommerce; ProductUserId for lobbies/sessions/P2P/RTC/product services; provider IDs/tickets for external credentials; UE FUniqueNetIdEOS for OSS adapters. Product state should not rely on parsing a combined string instead of typed identifiers.

### 3. Steam ticket supply and EAS choice

- `GetPlatformOSS()` uses the platform OSS and falls back to `IOnlineSubsystem::Get(STEAM_SUBSYSTEM)` on desktop (`:268-280`). `GetPlatformAuthToken()` requests `GetLinkedAccountAuthToken` with token type Session for Steam (`:302-311`).
- Legacy configured platform Connect path (`:1241-1307`) obtains the ticket, maps platform credential type, invokes Connect login and creates a PUID on InvalidUser. This is Steam identity backed by EOS product services.
- AutoLogin_SteamLogin (`:1914-1953`) gets a ticket and requires a string token. Connect-only selection copies AuthToken.TokenString into credentials. **The EAS branch sets the Steam external-auth encoded type but does not assign TempDetails.Token before calling Login.** This is an observable path inconsistency; runtime impact untested. Do not promise every Steam login variant works from the presence of a Steam enum.
- Legacy convenience `UEIK_Subsystem::LoginWithSteam` passes plain `steam` (`Subsystem/EIK_Subsystem.cpp:78-80`). In Login, this logs an encoded-format warning and falls through to settings-dependent legacy dispatch; it does **not** index part 1 in the initial dispatcher (`UserManagerEOS.cpp:713-738`). Some settings select the separate platform-ticket path (`:740-760`); if execution instead reaches the plain-type Connect branch (`:762-765`), LoginViaConnectInterface indexes missing part 1 (`:628-630`). The exact unconditional malformed-input example is bare `noeas`, which indexes missing part 1 in Login itself (`:715-717`). Bare `eas` instead reaches the size-checked Auth parser, logs an error, and retains default Epic/AccountPortal credential types (`:909-933`). These are distinct source-level paths; no runtime failure was reproduced.

### 4. Persistent auth, refresh, fallback and logout

- Persistent auth uses null ID/token and lets the EOS SDK keyring manage its cached token (`:833-844`). On InvalidAuth/AccessDenied/Auth_InvalidToken it deletes persistent auth and reports the original failure (`:874-900`; encoded path `:1028-1054`).
- AutoLogin parses AUTH_LOGIN, AUTH_PASSWORD, AUTH_TYPE (`:1710-1749`), then falls back to configured settings if credentials are absent. Settings include persistent auth/device/portal/platform/Steam/developer choices and a fallback (`:1774-1859,1914-1953,2014-2041`). Some enumerated platform cases have little/no body or commented code; enumerations are not evidence of implemented integration.
- Connect expiry calls RefreshConnectLogin. EAS refresh copies the current Auth token into Connect; non-EAS refresh requests another platform ticket (`:1363-1477`). The device branch checks literal `deviceid` while the newer guest flow stores `noeas_+_EIK_ECT_DEVICEID_ACCESS_TOKEN` (`:1371-1375`), making guest-refresh behavior a material verification gap.
- Auth logout performs EOS_Auth_Logout then deletes persistent auth and removes local user state (`:1618-1664`); Connect-only logout removes local state (`:1666-1671`). A replacement needs explicit semantics for “sign out,” “forget cached Epic login,” “unlink account,” and “delete device identity.” They are different operations here.

## Lobby/session/invitation flow traces

### Lobby create/search/join

`AsyncFunctions/Sessions/EIK_CreateLobby_AsyncFunction.cpp:16-76` maps capacity, invites, LAN, lobby voice, presence, visibility, join-in-progress, ID override and host-migration setting into FOnlineSessionSettings, then calls CreateSession. `OnlineSessionEOS.cpp:1106-1194` selects LAN, EOS lobby or EOS session backend. `:3928-4031` creates the EOS lobby with PUID, bucket, permissions, migration and RTC options; on success constructs UE session info/address, adds a voice lobby room and updates lobby metadata. EOS creates the lobby; EIK maintains the local UE session abstraction.

Search uses provider query handles/filters and copies provider details into FOnlineSessionSearchResults/cache (`OnlineSessionEOS.cpp:2247-2259,4531-4617`). Joining a lobby requires a valid cached details handle (`:4057-4077`), calls EOS_Lobby_JoinLobby and updates voice/local session state on completion (`:4087-4127`). The join callback clears the entire lobby search-result cache (`:4123-4124`), an important lifetime/concurrent-operation constraint.

`EIK_JoinSession_AsyncFunction.cpp:24-31` calls OSS JoinSession; `:84-120` resolves the address and calls APlayerController::ClientTravel, then immediately reports success. This proves travel was requested, not that world load/network admission/replication succeeded. Party sessions return success without travel (`:71-82`). For dedicated sessions it rewrites address with PortInfo, default 7777 (`:95-105`).

Sessions use EOS session modification/update semantics (`OnlineSessionEOS.cpp:1459-1581`) and have explicit start/end/register/unregister flows. EOS lobbies and sessions should not be collapsed into one ECS entity type merely because the EIK helper calls both “session.” Local operation state and remote provider resource state are distinct.

### Two different invitation kinds

**Friendship request:** EpicAccountId -> EOS_Friends_SendInvite/AcceptInvite/RejectInvite (`UserManagerEOS.cpp:3085-3205`). The friends list query also maps returned Epic IDs and asynchronously loads user information (`:2925-3020`). A Connect-only PUID is insufficient for these calls.

**Join invitation:** sender/receiver ProductUserIds -> EOS_Lobby_SendInvite or EOS_Sessions_SendInvite depending on the session backend (`OnlineSessionEOS.cpp:2902-3001`). A raw send method returns initiation success while provider completion is later; treat that distinction explicitly in replacement results.

The high-level lobby notification setup skips LobbyInviteReceived on the assumption it appears through system UI (`:720`) but installs accepted/join-accepted notifications (`:723-754`). Low-level `EIK_LobbySubsystem.cpp:117-146` exposes invite-received notification with IDs, allowing a custom inbox/UI. `:381-414` exposes count/index inventory after QueryInvites.

On invitation acceptance, `OnlineSessionEOS.cpp:990-1023` validates the local identity, copies lobby details by InviteId, fills a search result and emits OnSessionUserInviteAccepted. Joining through overlay presence instead uses UiEventId (`:1026-1058`). `Subsystem/EIK_Subsystem.cpp:20-30,1252-1257` forwards the OSS delegate to a Blueprint multicast. The explicit helper `EIK_BlueprintFunctions.cpp:422-430` invokes the same acceptance/details path; it does not itself connect a gameplay world.

There is an older auto-join handler body (`Subsystem/EIK_Subsystem.cpp:1228-1242`) but the initialized callback is `FuncEK_OnSessionUserInviteAccepted`, which broadcasts to game code. Do not attribute automatic join/travel to an unused handler merely because its source exists.

### Cold start and deferred acceptance

Source-wide command-line searches identified auth/artifact/deployment/sandbox parsing, but no general lobby-invite launch-argument or Steam GameLobbyJoinRequested processing path. Known-user prerequisite failures return a failed invitation result (`OnlineSessionEOS.cpp:990-997,1026-1033`) rather than storing a pending intent to retry after login.

SDK invite query/count/details and notification primitives exist; EOS launcher delivery may also supply notifications after login. Their presence does not prove a complete cold-start flow. Required evidence remains: app closed -> friend invite accepted -> correct app launched -> correct account logged in -> retained invite resolved once -> joining selected -> travel/network admitted. Steam invites and Epic invites need separate platform tests. A replacement should own deferred join intent, login gating, stale/expired invite rejection, deduplication and cancellation; this is an inferred product requirement, not a claim that EIK implements it.

### Host migration extent

EOS chooses/promotes the lobby owner when allowed by creation settings. EIK handles EOS_LMS_PROMOTED (`OnlineSessionEOS.cpp:904-970`), sets OwningUserId/OwningUserName/bHosting for the promoted local user, calls UpdateLobbySession, and emits a callback for the promoted user or remaining participants. It synthesizes `EOS:<PUID>:GameNetDriver:26`.

No inspected migration code serializes gameplay state, recovers the Unreal authority world, restarts a listen host, elects game authority independently, recreates replicated actors/entities, rejoins clients, or proves continuity after a host crash. “Basic Host Migration” here is **lobby owner notification plus session metadata/address glue**. Provider lobby continuity is not gameplay continuity.

## Chat and voice distinction

### Text/data

The OSS Chat and Message interfaces return nullptr (`OnlineSubsystemEOS.h:99-100`); external SendMessage UI is unimplemented (`UserManagerEOS.cpp:2744-2748`). Source search found support-ticket/anti-cheat “messages,” which are not player chat.

Actual multiplayer data primitives do exist: `EIK_RTCSubsystem.cpp:944-967` registers EOS_RTCData receive callbacks, copies bytes and returns local user/room/participant identity; `:1024-1047` sends a nonempty byte array into a room. `EIK_P2PSubsystem.cpp:491-517` exposes addressed packets with socket/channel/reliability/delayed-delivery options. These can support a custom room-chat protocol, but the game must define encoding/versioning, payload bounds, sender attribution, duplicate/order rules, channels, local mute/block policy, rate limits, text presentation and moderation. Durable/offline friends DMs require a separate design/service; no such service was identified here.

RTC data callbacks are stored in a single member delegate (`EIK_RTCSubsystem.cpp:947`) even though AddNotify returns separate notification handles. Multiple subscribers/rooms may overwrite the delegate while old notifications remain live. The replacement should use notification-owned callback registrations and normalize callback threading/lifetime before emitting ECS requests/signals.

### Voice and spatial output

`FEOSVoiceChatUser::Login` (`EOSVoiceChatUser.cpp:344-409`) validates/logically registers an already-known PUID with the voice layer; it is not another EOS identity login. Standalone channel join decodes supplied channel credentials and invokes EOS_RTC_JoinRoom (`:516-619`). Lobby create/join obtains the associated lobby RTC room automatically through AddLobbyRoom when compiled with RTC (`OnlineSessionEOS.cpp:4007-4011,4099-4103`).

There are microphone input/output device selectors, per-user volume/mute, transmit options, room membership and participant notifications. REST room token creation is an HTTP operation with caller authorization, not proof that a client should contain the credential able to create tokens (`EIK_API_CreateRoomTokens.cpp:7-58`).

“Positional Voice Chat” is not established by the existence of Set3DPosition: UE 5.6's implementation is empty and the previous implementation is behind EOS_VOICE_TODO, defined 0 (`EOSVoiceChatUser.cpp:34,662-685`). The concrete custom spatial path is AudioBeforeRender -> choose `GEngine->GetWorldContexts().Last().World()` -> scan GameState.PlayerArray -> match PlayerState net ID/PUID -> find Pawn -> find UEIKVoiceChatSynthComponent -> enqueue PCM -> clear EOS render buffer (`:2488-2562`). UE audio/synth component configuration supplies spatial playback. The subsystem positional update timer is commented out (`EIK_Voice_Subsystem.cpp:51-57`).

For ECS replacement, retain an Unreal audio component/render bridge where UE requires it, but map PUID to an explicit speaker entity/audio sink rather than searching PlayerState/Pawn/global last-world state. No per-player Actor is required by EOS identity, lobby membership or RTC transport itself.

## Concrete source caveats to retain in replacement planning

These are static observations/inferred risks, not reproduced defects and not a complete security review.

1. **Encoded credential parsing is not total.** Bare `noeas` (or `noeas_+_` with its empty second part culled) passes the initial nonempty test then indexes absent part 1 (`UserManagerEOS.cpp:713-717`). LoginViaConnectInterface similarly indexes part 1 for any one-part string that reaches it (`:628-630`); reaching it from plain `steam` depends on settings/OSS dispatch (`:740-765`). Bare `eas` does not have that indexing defect: its Auth parser checks part counts, logs malformed input, and retains default Epic/AccountPortal types (`:909-933`). A typed request API should reject malformed inputs explicitly instead of crashing or silently continuing with defaults. These observations are static, not reproduced defects.
2. **Local user 0 assumptions.** Connect node, CreateConnectID, completion and platform auto-login frequently force user 0 (`EIK_Login_AsyncFunction.cpp:39`; `UserManagerEOS.cpp:491,604,667,1069,1916`). Do not claim split-screen/multiple local identity coverage.
3. **Automatic account creation.** InvalidUser in Connect automatically creates a new PUID (`UserManagerEOS.cpp:1085-1087,1291-1294,1340-1343`). Account linking/upgrade UX must choose this intentionally to avoid fragmented identities/progression.
4. **Steam EAS ticket and guest refresh gaps.** Encoded Steam EAS branch omits assignment of the retrieved ticket (`:1940-1949`); guest refresh uses a legacy literal (`:1371`). Both require real-path verification.
5. **Raw buffer allocation/lifetime.** Login credentials allocate token/display name/id char arrays (`:645-660,980-992`), with no corresponding release visible in these functions. Avoid copying this ownership style.
6. **Member settings construction is discarded.** High-level CreateLobby builds LocalMemberSettings (`EIK_CreateLobby_AsyncFunction.cpp:35-44`) but does not assign it to SessionCreationInfo. Low-level member attribute APIs still exist; do not infer the high-level argument works.
7. **Party join success precedes checking provider result.** IsPartySession path returns success before Result is checked (`EIK_JoinSession_AsyncFunction.cpp:71-84`). Preserve actual result before applying travel policy.
8. **World/subsystem inconsistencies.** Some calls explicitly use world EIK subsystem but their completion reads default IOnlineSubsystem (`EIK_CreateLobby_AsyncFunction.cpp:18,117`; Join helper `:26,88`). Multi-world/PIE/provider coexistence needs explicit context ownership.
9. **Completion initiation vs semantic completion.** Login/session helpers frequently ignore immediate false return from the OSS call and subscribe to broad delegates. High-level join reports success immediately after ClientTravel, not network admission. The operation layer needs correlation IDs, one terminal result, cancellation and distinct lobby/world readiness.
10. **Shared callback slots/cache.** RTCData notification delegate is a single member (`EIK_RTCSubsystem.cpp:947`); successful join resets all lobby-search cache (`OnlineSessionEOS.cpp:4123-4124`); invitation handlers use LastInviteSearch shared state (`:1012-1016`). Explicit per-operation resources are safer than cross-operation mutable state.
11. **Host migration has hardcoded transport address.** GameNetDriver:26 (`OnlineSessionEOS.cpp:928-958`) differs from the driver-derived names/channels in NetDriverEIKBase (`:116-124`). No seamless migration claim is justified without reconnect/state tests.
12. **Spatial voice uses global last world and Actors.** WorldContexts.Last can be wrong in multi-world/editor situations; remote identity lookup scans PlayerState/Pawn on audio callbacks (`EOSVoiceChatUser.cpp:2498-2551`). Thread/world ownership and sample handoff need verification. Components present but inactive/unsupported cause the EOS audio buffer to be cleared anyway (`:2538-2562`), potentially silencing that speaker.
13. **HTTP response boolean means transport success.** EIK_BaseWebApi emits true for any valid HTTP response and supplies the response code (`:8-23`); consumers must interpret 4xx/5xx. Portal administrative endpoints are not a client-safe authorization architecture by themselves.
14. **Declared interfaces include stubs.** IOnlineParty, Chat, Message, groups/tournament etc return nullptr; StartMatchmaking, ShowInviteUI, ShowSendMessageUI and block/unblock explicitly report unsupported (`OnlineSubsystemEOS.h:94-102`; `UserManagerEOS.cpp:2664,2744,3343,3364`; `OnlineSessionEOS.cpp:2100-2129`).
